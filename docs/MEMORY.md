# Memory and full-quality streaming

Measured on the physical M4 on 7 October 2026. The objective is the supplied game's original texture detail, alpha, HDR range and mip chains. Lower mip settings are diagnostic only.

## Findings

- Physical memory reported by the device: 16,165,289,984 bytes. With increased memory, extended addressing and development debugging memory requested, `phys_footprint + os_proc_available_memory()` stayed near **6 GiB** during these runs. Both the signed app and its signature-verified provisioning profile contain these capabilities. This is an observed budget, not a universal iPad limit. Extended addressing does not itself supply physical memory. Apple's [increased-memory entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.kernel.increased-memory-limit?changes=_4) requires measuring available headroom.
- Metal reports BC compression supported. BC1, BC3, BC7 and unsigned BC6H textures allocate successfully; a synthetic BC1 red block decodes to the expected RGBA pixel through a GPU compute/readback check. The stock Unity 2020.3.12f1 iOS backend rejects all four. Our derived Metal format bridge now reports all four supported in the original game runtime and eliminates its unsupported-format decompression warnings. Apple's [Metal tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf) place M4 in Apple9, which supports BC formats.
- Static inspection of 1,952 serialized files found 5,190 nonempty Texture2D objects: **one** enables Unity mip streaming, 5,145 use external resource files, and 45 retain readability. The 3,787 DXT/BC objects occupy an estimated **1.59 GiB** as full compressed mip chains versus **8.29 GiB** after RGBA32 fallback. This is an aggregate across containers, without deduplication; it is not simultaneous residency. Cubemaps, virtual textures, allocator overhead and temporary decode buffers are excluded.
- In a full-resolution diagnostic, Unity's texture counter reported about **150 MiB** at a memory warning while process footprint was about **4.8 GiB**. The process later disappeared near 5.54 GiB footprint. A later debugger-attached run establishes `EXC_RESOURCE`: the process exceeds a **6,144 MB** memory watermark. Texture counters may omit transient work; the static expansion estimate cannot be used to attribute the entire loading spike.
- A subsequent full-resolution run resolved the native profiler bindings despite stripped managed getters. At its warning: footprint **4.81 GiB**, graphics-driver allocations **2.72 GiB**, Unity allocated **718 MiB** / reserved **843 MiB**, and original IL2CPP managed used **700 MiB** / heap **716 MiB**. Counters can overlap and are not additive. Graphics allocations are a substantial lead, but the texture-streaming counter alone underrepresents them. Decode/upload overlap and other GPU resources still need allocation tracing.
- With the BC bridge enabled at full resolution, the game loads the Lobby and begins Whirling floor 2. At a warning near 4.80 GiB footprint, graphics-driver allocation is **1.47 GiB**, Unity allocated/reserved is **1.82/2.12 GiB**, managed used/heap is **588/764 MiB**, and the texture counter is **370 MiB**. This is a different loading stage from the baseline; the counters do not establish a percentage reduction. A later full-resolution run reaches the original main menu, with frames advancing to 3,114 at 60.633 seconds and footprint stabilizing near **4.94 GiB**. Its GPU capture confirms menu rendering, with an orientation/layout problem. The user reproduced termination via **New Game → Thinker → Continue**; the debugger again reports the 6,144 MB watermark. The final captured stack runs through `CharacterAnalogueControl::Start` and `InteractableSelectionManager::.ctor` into IL2CPP class metadata allocation and memory clearing. The final allocation is not necessarily the dominant source. The reproduced transition's main-thread stack is in the scene-loading coroutine calling `System.GC::Collect`; the reported resource-exception thread is a Metal command-queue thread. These stop locations do not prove GC or that queue owns the dominant allocation. AmplifyTextureNative remains absent.
- Serialized metadata totals about 15.7 MiB. There are 3,889 stored type-tree instances containing 180,093 nodes, with 34 distinct structures containing 8,518 nodes. Structural equality is an audit result, not permission to merge different script/type identities.

Reproduce the static census with `make inspect-texture-memory`. Per-object results and device logs remain under ignored `artifacts/`.

## Confirmed loading changes

Static ARM64 analysis and live scene enumeration established that the original menu retains **33 scenes**. `FastLoadManager` loads the first admitted world scene in Single mode, then preloads the others additively. Normal transitions toggle object activity and reuse its scene dictionary; inactive scenes remain resident.

The original host now validates and adapts the two scene coroutine methods through writable runtime metadata. It retains the first Single-mode bootstrap and Lobby, defers the other build scenes, and inserts an on-demand loaded scene into the original dictionary before resuming the original transition. On M4, the menu now has **2 loaded scenes**, about **2.5 GiB** footprint; Whirling floor 2 makes 3 scenes. Texture blocks, mip levels and scene object bodies are unchanged. Visited scenes are still retained. Eviction needs a complete NPC/item/save-state audit; canceled pending loads also need cleanup. This is not yet a bounded full-session policy.

Lazy loading alone still hit the 6,144 MB watermark. The matching debugger stack now identifies `AmplifyTexture.PhysicalCache::SafeAllocatePages` constructing Texture2D objects; the runtime repeatedly reports its absent native decoder during initialization. The derived original ARM64 Amplify CPU plugin now loads, and those missing-plugin errors disappear. Its codec executable bytes are unchanged. Desktop OpenGL imports resolve to original explicit failure guards; no fake readback or GPU result is returned. The current game path has not entered those guards. This establishes CPU integration, not completion of every Amplify GPU path.

With both changes, the user confirmed opening dialogue, textured room rendering and tap-to-move after **New Game → Thinker → Continue**. Initial room samples hold near **4.0 GiB**, with about **2.0 GiB** available headroom. The user subsequently confirmed saving and area transitions; a GPU frame shows Harry and Kim outside. Retained areas reach about **5.1 GiB**, with about **0.9 GiB** remaining. Full fidelity comparisons and long play remain unverified. Full 4:3 landscape framing and UI alignment are now device-verified.

Live entitlement inspection reports increased memory and extended addressing enabled. A separate build without the debugging-memory entitlement still reports about **6 GiB** footprint plus available memory, already before Unity initializes. The read-only kernel-limit query is denied (`EPERM`). Removing the debugging entitlement does not establish a larger limit; the reason for this iPadOS/device policy remains unresolved. Signing eligibility and physical RAM do not themselves establish the granted app limit. No kernel-limit setter is used.

## Why streaming still decompresses

These are separate operations:

1. **Bundle compression:** LZ4 permits chunk reads; LZMA may require whole-bundle decompression. Our derived bundles are LZ4, but disk savings do not determine GPU residency. See [Unity bundle compression](https://docs.unity3d.com/2020.3/Documentation/Manual/AssetBundles-Cache.html).
2. **Crunch:** loading expands Crunch into its underlying DXT blocks. On a compatible GPU those blocks remain compressed until sampling.
3. **GPU format fallback:** the stock old iOS engine rejects DXT/BC, so it expands loaded textures into supported pixel formats. RGBA32 costs roughly four times DXT5/BC7 or eight times DXT1 at the same dimensions. Loading one area at a time still incurs that area's expansion. See [Unity 2020 format support](https://docs.unity3d.com/2020.3/Documentation/Manual/class-TextureImporterOverride.html).
4. **Residency:** an external `.resS` payload is not a mip-streaming policy. Unity requires global streaming configuration and per-texture flags; nonstreaming textures can exceed the streaming budget. The game's Amplify VTC page system is another independent mechanism, and its desktop OpenGL plugin is still incompatible. See [Unity mip streaming](https://docs.unity3d.com/2020.3/Documentation/Manual/TextureStreaming.html).

## Implementation order

1. Attribute startup peaks using process footprint, managed heap, Unity allocations, graphics allocations and texture counters. Separate steady residency from decode/upload overlap, duplicate loads and retained bundles. Process sampling now runs for 20 minutes, with periodic bounded VM-region residency accounting by OS tag; main-thread Unity/managed counters run every five seconds. The diagnostic-only region query is resolved dynamically because it is absent from the public iOS link stubs; it reports absence instead of blocking startup. Shared mappings may be counted more than once, so region totals are not an additive footprint estimate. The device scan succeeds with 16 KiB pages. At one near-warning sample, IOAccelerator-tagged residency is about 1.54 GiB; malloc large/small tags are about 1.14/0.97 GiB; untagged residency is about 2.33 GiB. These totals overlap and do not identify individual allocation owners. System allocator pressure relief at the warning releases **zero bytes**, so trimming its free cache has not established a fix. Main-thread counters cannot sample while loading blocks that thread.
2. Validate the experimental native BC path now implemented in the pinned engine: capability flags, Unity-to-Metal format mapping, block pitches/sizes, upload, mip handling and sampling. Changing only `SupportsTextureFormat` is insufficient. Preserve original BC blocks; uncrunch into those blocks without a second lossy encoding. Validate real asset readbacks, sRGB/linear variants, alpha, HDR and mip transitions before treating the experimental game path as visually verified.
3. Validate the integrated Amplify CPU/page path across actual camera movement and establish a bounded residency cache, keeping the full source on disk. Use visibility and camera-motion prefetch, bounded decode/upload buffers and GPU-completion fences before eviction. Retain all original levels; wait for required detail during transitions instead of silently forcing a lower-resolution image.
4. Audit area/addressable ownership and release unused resources without unloading live references. Consider type-tree reuse only with validated identity/ownership. Unity's [6.3 report](https://unity.com/blog/unity-6-3-lts-is-now-available) cites a 97% reduction in Disco Elysium's **type-tree** memory, not total game memory. A new engine is not an ABI-compatible drop-in replacement for the original IL2CPP module; 2020.3.12f1 remains the compatibility target.

The fast storage is useful for a bounded working set. Apple's [sparse-texture sample](https://developer.apple.com/documentation/metal/streaming-large-images-with-metal-sparse-textures) and [fast resource loading](https://developer.apple.com/videos/play/wwdc2022/10104/) describe tile residency and asynchronous disk-to-GPU transfers. Those APIs require explicit integration; they do not make arbitrary Unity heap or GPU allocations disk-backed. System swap, where available, is supplemental rather than a residency plan. Actual storage throughput and streaming deadlines have not been measured.

ASTC 4×4 is a possible compatibility fallback, but re-encoding existing BC textures can add loss. The pinned encoder is installed for experiments; no conversion is enabled. Exact preservation favors the original BC path. Keep source resolution, mip content, color space, alpha and HDR semantics; validate representative real-game frames and camera transitions, not only codec metrics.

## BC options

| Route | Quality and integration |
| --- | --- |
| Build-time BC support in the pinned Metal backend | Implemented experimental format/capability bridge, checked against the exact Metal object hash. Original blocks and runtime remain unchanged; game fallback warnings disappear. Real-asset color, alpha, HDR and mip fidelity checks remain. |
| Native Metal textures with Unity external-texture integration | Preserve blocks; requires interception before Unity fallback and correct ownership, formats, material bindings and mip updates. Creating a BC Metal texture alone does not prevent Unity's loader expanding its copy. |
| Custom renderer or shader decoding from BC buffers | Preserve compressed source, but requires substantial shader/material and sampling integration; filtering and derivatives must match. |
| Newer Unity player | Requires a separate native BC capability test and original-runtime/engine ABI audit. A version change is not an established fix: Unity's current [texture support table](https://docs.unity.com/en-us/engine/6000.5/manual/materials-and-shaders/textures/textures-getting-started/texture-compression-formats/texture-formats-reference) still lists BC unsupported for iOS/tvOS. Documentation may lag hardware; test the player before investing in migration. |

BC is decoded by the GPU when sampled even on the native path. The objective is avoiding a persistent expanded texture and large CPU decode/upload copies, not eliminating decoding entirely.

The [official Switch release](https://www.nintendo.com/us/whatsnew/disco-elysium-the-final-cut-is-out-now-for-nintendo-switch/) establishes that the game has a constrained-platform port. ZA/UM also documented [scene-load optimizations](https://discoelysium.com/devblog/2022/02/07/jamais-vu-update-huge-thanks-for-2021). Neither source exposes its exact memory budgets, asset formats or fidelity compromises. The Switch demonstrates feasibility of adaptation; it does not establish that the supplied Mac payload and loading behavior already fit unchanged.
