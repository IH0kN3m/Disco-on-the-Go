# Disco Elysium native iPad port feasibility

Porting the supplied Disco Elysium game to an iPad Pro M4 is plausible as a substantial reverse engineering project. The existing ARM64 code is useful, but it does not make the macOS application compatible with iPadOS. With only the compiled app, the decisive questions are whether its gameplay logic can be reused or recovered, and whether its textures, shaders, and serialized scenes can be rebuilt for an iPad runtime.

The target is the full game running locally with touch controls. The working assumption is a standard iPadOS device using a signed development app. Streaming and a simplified adaptation are outside this target. This assessment is based on static inspection on 6 October 2026; successful iPad execution and performance remain unproven.

Xcode, clang, and an iPhoneOS SDK are available on the development Mac. This establishes that native compilation tools exist, but does not establish compatibility between Unity 2020.3.12f1 and the installed toolchain.

## Why ARM64 alone is insufficient

The instruction set is one layer of compatibility. The engine also depends on its operating system, application lifecycle, graphics APIs, binary imports, and runtime interfaces. Apple explicitly distinguishes architecture checks from platform checks when sharing code between macOS and iOS. [Apple universal binary documentation](https://developer.apple.com/documentation/apple-silicon/building-a-universal-macos-binary)

The supplied UnityPlayer links AppKit, Cocoa, Carbon, desktop OpenGL, and other macOS frameworks. InControlNative also links AppKit and IOKit. These dependencies require replacement or substantial adaptation for the target. GameAssembly's direct framework imports are narrower, including Foundation, CoreFoundation, and Security, which makes isolated game-code reuse a reasonable experiment. That observation is not proof of iOS compatibility: its embedded IL2CPP runtime still contains platform-specific behavior.

Changing a Mach-O platform marker, removing the Intel slice, or repackaging the app as an IPA would leave those dependencies and runtime assumptions unresolved. Unity normally builds an iOS-specific UnityFramework with an iOS launcher and native libraries. Its documented application embedding interface does not provide a supported way to insert an unrelated macOS GameAssembly. [Unity 2020.3 Xcode project structure](https://docs.unity3d.com/2020.3/Documentation/Manual/StructureOfXcodeProject.html)

## Candidate implementation routes

| Route | What it requires | Assessment |
| --- | --- | --- |
| Reconstruct a Unity project | Recover scenes and assets, recover or reimplement executable script bodies, replace native plugins, rebuild for iOS | Best maintainability if enough gameplay logic can be recovered; considerable manual work is likely |
| Reuse selected ARM64 gameplay code | Adapt binary linkage and platform dependencies, retain compatible IL2CPP object layouts, connect engine calls to an iOS runtime, fix platform branches | Worth a bounded experiment because gameplay code is more isolated than the engine; highest uncertainty is runtime integration |
| Lift native code and recompile | Map function boundaries, recover control flow, pointers, globals, exceptions, generics, callbacks, and external interfaces | A possible research fallback, with no established automated pipeline for this exact game |
| Rewrite gameplay around recovered content | Reimplement dialogue evaluation, state, checks, movement, inventory, quests, animation, saves, and UI behavior | Broad control over the result, but full fidelity and completion require a large validation effort |
| Port the complete macOS Unity engine binary | Recreate macOS platform services and adapt graphics, input, audio, lifecycle, and runtime loading | Poor first investment compared with using an existing iOS Unity engine |

The preferred investigation combines project reconstruction with a small game-code reuse experiment. Preserve reusable data and behavior before choosing a full rewrite. Reusing ARM64 instructions may reduce code recovery work; it cannot remove the need for an iOS engine and compatible assets.

IL2CPP metadata recovery and executable code recovery must be measured separately. Il2CppDumper restores types and signatures but explicitly excludes method code. Cpp2IL attempts method-body recovery, supports ARM64 analysis, and describes its decompiler as work in progress. A generated DLL containing stub methods is useful for serialization and analysis but cannot run the game. [Il2CppDumper](https://github.com/Perfare/Il2CppDumper/blob/master/README.md), [Cpp2IL](https://github.com/SamboyCoding/Cpp2IL)

AssetRipper is a candidate for recovering Unity assets into an editable project. Its stated Unity version range includes this build, but successful extraction and preservation of this game's references must be tested. [AssetRipper](https://github.com/AssetRipper/AssetRipper)

## Rendering and content recovery

macOS AssetBundles contain platform-specific assets. Merely renaming StandaloneOSX directories to iOS cannot convert their textures or shaders. Recover source-equivalent assets, rebuild iOS bundles and catalog entries, and validate dependencies. Preserve readable content such as dialogue and localization where extraction permits it. [Unity AssetBundles documentation](https://docs.unity3d.com/2020.3/Documentation/Manual/AssetBundlesIntro.html)

Amplify is an early critical dependency. The supplied native plugin links desktop OpenGL and exports page decoding, BC texture decoding, transcoding, and GPU readback functions. Those exports suggest useful boundaries for analysis, but they do not establish the format of each texture file or the graphics path the game actually uses.

Amplify's public product page advertises desktop support and marks iOS support as coming. This is a reason to plan for replacement; it does not prove whether ZA/UM had a private platform implementation. [Amplify Texture](https://amplify.pt/unity/amplify-texture-2/)

Test two options on one representative environment: decode the virtual textures into conventional textures with mipmaps and rebuilt materials, or preserve page-based streaming through an iPad-compatible Metal implementation. Whole-texture conversion may be simpler but must stay within memory limits. Do not decompress the entire virtual texture collection into memory.

Shaders need separate reconstruction or replacement where recoverable source is unavailable. A scene's appearance also depends on material parameters, lighting, render ordering, postprocessing, and camera behavior. Compare a reconstructed scene with the Mac build before scaling extraction to the full game.

Native store integrations need platform-specific treatment after identifying active calls. Replace desktop file dialogs, adapt persistent paths, and handle controller APIs through iPad-compatible code. Essential texture functions cannot be discarded alongside optional achievements or cloud features. Unity's documented iOS plugin workflow uses iOS-native source and libraries with corresponding managed bindings. [Unity iOS plugins](https://docs.unity3d.com/2020.3/Documentation/Manual/PluginsForIOS.html)

## Touch controls

Build a shared action layer for touch, controller, and mouse input. Start with tap-based movement and interaction, then validate it against the actual game input methods. Unity's touch-related names in metadata do not prove that the shipped game already has usable touch controls.

| Interaction | Proposed touch behavior | Required validation |
| --- | --- | --- |
| Move and interact | Tap a destination, hotspot, or character | UI taps must never also trigger world movement |
| Examine and preview | Hold to show details or hotspot labels | Replace information otherwise available only on hover |
| Camera | Two-finger drag for pan and pinch for zoom where supported | Gestures must cancel pending taps and respect camera bounds |
| Dialogue | Tap choices and scroll the transcript | Avoid accidental selections during scrolling or voice playback |
| Inventory | Tap to inspect or equip; drag only for actions that benefit from it | Preserve tooltips and provide alternatives to precise dragging |
| Menus | Visible touch targets for map, journal, inventory, pause, and saves | No essential action should require a keyboard |

Convert input coordinates through the actual game viewport, including scaling and any letterboxing. Use explicit gesture cancellation when touches are interrupted. Design text and hit targets in device points rather than raw display pixels. Keep text scalable, separate world rendering resolution from UI resolution, and accommodate the iPad aspect ratio and system gesture area.

An initial cursor-emulation layer could exercise existing click paths. The finished interface needs readable dialogue, hover alternatives, gesture conflict handling, and reliable UI priority. Add touch in the first playable scene so input problems are discovered before broad content recovery.

## iPad Pro M4 constraints

M4 is a plausible hardware target, but this build has no measured iPad performance. Both sizes have a 10-core GPU. The 256/512 GB models have 8 GB RAM and a 9-core CPU; the 1/2 TB models have 16 GB RAM and a 10-core CPU. Total device RAM is not an application's guaranteed memory allowance. [Apple 11 inch specifications](https://support.apple.com/en-us/119892), [Apple 13 inch specifications](https://support.apple.com/en-us/119891)

The 11 inch display is 2420 × 1668; the 13 inch display is 2752 × 2064. Both support refresh rates up to 120 Hz. Begin with a proposed stable 30 fps target and scalable world resolution, then evaluate 60 fps after profiling. A 120 Hz panel does not establish a suitable 120 fps game budget. [Apple 11 inch specifications](https://support.apple.com/en-us/119892), [Apple 13 inch specifications](https://support.apple.com/en-us/119891)

Measure resident memory, peak scene-transition memory, texture cache usage, frame times, load times, and thermal behavior on the actual iPad. Test background and foreground transitions, audio interruption, autosaves, and relaunch recovery. Exact display size, storage tier, iPadOS version, and available signing setup are implementation inputs still to resolve.

## Feasibility milestones

| Milestone | Concrete work | Evidence required to proceed |
| --- | --- | --- |
| Recover the program map | Thin copies of both architecture slices; map IL2CPP types, registrations, method addresses, plugin calls, input, dialogue, saves, and Amplify | Named method map and a list of active platform dependencies |
| Recover representative behavior | Examine methods involving simple logic, branching, objects, collections, generics, and coroutines; compare ARM64 and x86_64 analysis where helpful | Correct behavior on explicit inputs, rather than successful generation of stub DLLs |
| Recover representative content | Extract one scene and its dependencies, a dialogue database, UI elements, and an Amplify texture sample | Rebuilt scene loads with preserved object references and recognizable visuals |
| Test an iOS host | Build a minimal iOS Unity host; independently test selected reused or recovered game logic, runtime integration, and texture conversion | Signed execution on the actual iPad with correct outputs and rendering |
| Build a playable slice | One room, movement, one complete conversation, a state-changing interaction, audio, and save/load with touch | State survives relaunch; all required interactions work without keyboard input |
| Expand and optimize | Recover remaining scenes and gameplay systems; validate dialogue conditions, branching, quests, inventory, saves, and transitions | Broader progression tests, sustained device profiling, and fidelity comparisons |

A loaded library is not proof that Unity can run its scripts. A recovered scene is not proof that gameplay code exists. A rendered room is not proof of story progression or reliable saves. Keep these acceptance criteria separate.

If selected game-code reuse succeeds, expand it while converting content and replacing platform services. If reuse fails but method recovery is useful, prioritize reconstructed C# and selective rewrites. If both fail broadly, revise the scope and effort estimate around a substantial gameplay reimplementation.

## Effort and immediate next step

Use an initial one to two engineering weeks as a proposed investigation budget for method mapping, representative recovery, texture decoding, and an iOS host experiment. This is a planning allowance, not a prediction that all tests will succeed in that time. A successful path would still imply months of integration and fidelity testing. A broad gameplay rewrite could require a small team and a year or more; a responsible full schedule depends on measured recovery coverage.

The next deliverable should be the method and dependency map plus a recoverable scene sample. Those results will let us choose between ARM64 code reuse, reconstructed Unity scripts, and selective rewrites before committing to a full implementation. The port itself has not been demonstrated by this initial audit.
